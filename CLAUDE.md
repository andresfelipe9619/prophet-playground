# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

It is the condensed version. Full documentation lives in [`docs/`](docs/README.md) — start with [`docs/domain-and-premise.md`](docs/domain-and-premise.md), which explains why several decisions here look wrong until you know the premise. When you change behaviour that these notes describe, update the matching page in `docs/` too.

## What this project is

Analysis and forecasting over historical Colombian Baloto lottery results. A ticket is 5 distinct numbers from 1-43 plus one "superbalota" from 1-16; draws run Monday, Wednesday and Saturday.

**The repository is split by domain.** `core/` holds evaluation machinery that knows nothing about lotteries — walk-forward splits, the z-test against a null, the multiple-comparison correction. `lottery/`, `football/` and `cycling/` are sibling domains that supply `core/` with the two things it deliberately lacks: the null distribution to compare against and the scoring rule. **Do not put anything domain-specific in `core/`** — if it mentions a ball, a draw, a pool, a team, a match, a rider or a stage, it belongs in a domain package.

**Football and cycling invert the premise, not the discipline.** Baloto is i.i.d. by design and nothing can beat chance; football and cycling have real signal and a model genuinely can predict. What does not change is that a prediction is worth nothing until it beats a baseline named in advance. In football that baseline is the **closing betting line**, and it is brutally hard — a model that beats an Elo rating but loses to the market has found nothing. See [`docs/football.md`](docs/football.md). Football has `football/dixon_coles.py` (attack/defence strengths, the low-score correction, one fit feeding 1X2 / correct score / O-U / BTTS), `football/elo.py` (the cheap baseline, with an ordered logit fitted for the draw), `football/ensemble.py` (pooling a model with the market), the proper scoring rules in `football/scoring.py`, a paired one-sided market test in `football/evaluation.py`, a walk-forward `football/backtest.py` with `compare_models`, and `football/value.py` for edge and staking.

**Cycling predicts an ordering, not an outcome.** ~180 riders, most of whom cannot win, and a fifth of whom may not finish. Its baseline is the market where a price exists and otherwise the **pre-race ranking** (UCI/PCS points, start-list quality) — a uniform draw over the start list is not a baseline, it is a way to make any model look brilliant, and `cycling/baseline.py` implements it under that name so the mistake cannot be made silently. See [`docs/cycling.md`](docs/cycling.md). Now has the full layer: `cycling/baseline.py` (Plackett-Luce worths from points or prior form), `cycling/scoring.py` (the PL log score over the finishing order is the verdict; rank correlations are diagnostics), `cycling/plackett_luce.py` (rider strengths by MM, shrunk toward the field) and `cycling/evaluation.py` (the paired test against the ranking, plus the walk-forward). The market baseline now exists — `cycling/market.py` (de-margining an outright book, where the three normalisations disagree *enormously* because almost every runner is a longshot) and `cycling/prices.py` (the file contract, one book and one market per frame) — but **nothing fetches prices**, so in practice every verdict is still against the ranking and says so.

**The domain constraint that shapes the whole architecture:** lottery draws are i.i.d. uniform by design, so no model can beat chance. The codebase was deliberately refactored around this. Every model output is paired with the chance baseline it must beat, and every heuristic (hot/cold, "overdue" numbers) carries an explicit note that it has no predictive value. Do not "improve" a model by adding seasonalities, holiday regressors, or tuned hyperparameters that fit historical noise — that is the anti-pattern this repo was moved away from, and [`docs/domain-and-premise.md`](docs/domain-and-premise.md#6-anti-patterns) explains why. If a change makes a model look better on history without beating the chance baseline in `lottery/backtest.py`, it made the project worse.

Move the pin when the developed-on version moves; do not add a second entry beside it. **ruff** and **mypy `strict`** (over `core/`) are configured in [`pyproject.toml`](pyproject.toml) and run locally — `ruff check .` and `mypy`. They are not yet wired into the `static` job; the snippet is in [`docs/development.md`](docs/development.md#3-verification) and adding it needs a push with GitHub's `workflow` scope. The two scope decisions in the config are deliberate: ruff's line limit is **120** because this codebase carries its reasoning in prose (at 100 there are 454 violations, nearly all of them sentences), and mypy is scoped to `core/` because that is the one package with no DataFrames in its signatures and the one where a wrong type returns a number instead of an error.

CI installs [`requirements-test.txt`](requirements-test.txt), not `requirements.txt` — the suite never imports prophet, streamlit, plotly, matplotlib, seaborn or requests, which are reached only from the dashboard, the scripts, or lazily from inside a function body (`fetch_csv` in `football/downloader.py` and `fetch_page` in `cycling/scraper.py` import requests where they use it, so their parsers stay testable without the network). beautifulsoup4 *is* installed: `cycling/scraper.py` parses HTML at module scope and its tests run that parser against saved-style fixtures. prophet and cmdstanpy stay out because no test imports them, not because they are expensive — measured, prophet installs from a `manylinux` wheel in about 6 seconds (see [`docs/local-setup.md`](docs/local-setup.md)); an earlier note here claimed the install would dominate the job, which was true of prophet 0.x and is not true now. timesfm and torch are out for the same reason and one more: `tests/test_timesfm_model.py` drives the model through an injected stub forecaster, so the suite pins its invariants with neither installed. **If a new test needs one of them, add it to both files** — it will fail loudly with an ImportError rather than skipping quietly.

Changes are verified by:

1. `pytest`. The suite is deterministic (everything is built from the seeded generator in `lottery/utils/sample_data.py`) and pins the invariants listed below rather than chasing coverage — those are what a refactor breaks silently. Add to it when you add an invariant. `python -m py_compile <files>` still helps for files the suite does not import. There **is** a coverage floor (90%, measured at 92.6%, `[tool.coverage.*]` in `pyproject.toml`, enforced in CI), and it is a floor rather than a target: it catches a module landing with no tests at all and can say nothing about whether the invariants below are pinned — a suite can sit at 95% and still not notice `beats_chance_test` losing its one-sided p-value. `dashboard/` and `scripts/` are outside it on purpose; the dashboard's real check is a browser.
2. Running the affected module against synthetic data from `lottery.utils.sample_data.load_sample_and_preprocess()`, which returns the same `(df, balls_expanded)` shape as the real loader — no private CSVs needed.
3. `python -m lottery.utils.check_docs` after any documentation change — it reimplements github-slugger exactly, because headings here use `·` and `—` and GitHub removes those without collapsing the spaces they leave (`### 6 · Jugadas — generate` anchors as `6--jugadas--generate`, doubled hyphens). A checker that normalises hyphen runs passes links that 404 in the browser.
4. The `static` CI job byte-compiles `dashboard/app.py` and everything under `scripts/`, which pytest never imports — a syntax error there passes the whole suite and is caught only here.
5. For dashboard changes, launching Streamlit headless and driving it with Playwright (Chromium is under `/opt/pw-browsers/`, at a versioned path such as `/opt/pw-browsers/chromium-1194/chrome-linux/chrome`). Streamlit only executes the script when a client connects over the websocket, so an HTTP 200 on `/` proves nothing — you must load the page in a browser and check tab text for `Traceback` / "This app has encountered an error". Note that all tab panels stay mounted in the DOM, so scope Playwright locators to `get_by_role("tabpanel", name=...)` or they match across tabs.

`lottery/backtest.py` with `--include-prophet` refits Prophet per position per window. That sounds expensive and is not: measured at 20 windows over 1035 draws it is 44.9s without Prophet and 49.8s with, about +11% — an earlier note here called it "far slower", which was never measured. The CLI keeps the opt-in flag (a flag named `--include-prophet` that defaults to on is incoherent), but **the dashboard's backtest includes it by default**, because a comparison table missing a model silently compares five things while the correction says six.

**TimesFM is the exception, and is unticked in the dashboard.** The rule above is about *silence*, not about defaults: an unticked box with a sentence under it saying why is the reader's choice made before the cost, and the Bonferroni correction counts only the models that actually ran. TimesFM ticking itself was an ambush — a reader clicking "Ejecutar backtest" to see the other five paid a forward pass per window plus, on a first run, a checkpoint download of hundreds of MB, which on a machine without a GPU is minutes of apparently nothing happening. That is indistinguishable from a hung app, and it is what the reported "slow, then the dashboard disconnects" turned out to sit on top of.

## Data contract

Scripts read `exported_data/final-final.csv` — gitignored, not in the repo. Columns: `Date` (dd/mm/yyyy) and `Ball`, six dash-separated numbers where the **last one is the superbalota** (e.g. `3-12-19-27-41-8`). `lottery/utils/processor.py:preprocess_draws` is the single owner of that contract; `load_and_preprocess` (CSV **or a `.sqlite` store**), the dashboard's upload path and `lottery/utils/sample_data.py` all go through it. **The store replaces the file, not the contract**: `is_store` / `read_raw` / `import_csv` / `store_status` put the raw `Date`/`Ball` rows into `core/storage.py` and hand back the same rows a CSV would, so nothing downstream knows which it got. `import_csv` validates **before** it writes, which is the point of having a store. `python -m scripts.store_sync import|status|check` is the CLI; **`check` exits non-zero** when the store is missing, mis-versioned, or has no new draw in `--max-age-days` — a scraper whose markup changed keeps exiting 0 and appending nothing, and that is the failure a schedule exists to catch.

**Two eras of the game.** Baloto changed rules in April 2017 (before: 6 balls from 1-45, no superbalota). Both eras publish as six dash-separated numbers, so a long history has the same *shape* throughout and only the values give the mix away — a real 2010-2026 export splits 707/1035 across the change. `preprocess_draws` warns rather than raises (the rows are real draws; a caller may want them), and `format_violations` / `current_format_mask` / `check_draw_format` in the same module do the detection. Note the two masks differ deliberately: `format_violations` can only flag rows that are *provably* impossible today, so `current_format_mask` cuts at the date of the last violation instead — an old-era draw that happens to fit today's bounds would otherwise survive. Use `load_and_preprocess(..., current_format_only=True)`, `--current-format-only`, or the dashboard's sidebar checkbox (on by default).

`python -m lottery.utils.scraper --years 2020-2025` builds that file from loterias.com, merging into whatever is already there. Its parser raises rather than skipping on anything unexpected (no rows, wrong ball count, unknown month) — a scraper that silently writes an empty CSV when the markup changes is the failure mode this module is shaped to avoid. `parse_results_page(html)` takes HTML and does no I/O, so it can be tested against saved pages; nothing in the repo can verify it against the live site, so `--dry-run` exists to eyeball a scrape before writing.

When no real CSV is present the dashboard falls back to synthetic data and says so on screen.

## Cross-cutting invariants

**Position semantics.** Throughout the codebase a "position" is a column index into `balls_expanded`. `lottery/models/common.py` is the single source of truth for what each position means: `super_position(n_columns)` (the last column, range 1-16), `main_positions(n_columns)` (all the others, range 1-43), plus `range_for_position` / `clip_to_range` / `series_label`. Derive positions from those helpers rather than writing `n_columns - 1` or `range(5)` — the two only coincide when there are exactly 6 columns, and nothing else in the codebase assumes that. Any new model must clip its raw output through `clip_to_range` or it will emit out-of-range numbers.

Pool sizes (`MAIN_POOL`, `SUPER_POOL`), the draw calendar and `DEFAULT_DATA_PATH` also live in `common.py` and are imported, never re-declared.

**Two time axes.** Prophet and all display code use calendar dates (`ds`). statsforecast models use a sequential integer draw index instead, assigned in `lottery/models/common.py:to_long_format`, because draw days are 2 and 3 days apart and no fixed pandas frequency fits them. Never introduce a fixed `freq=` for future dates — use `next_draw_dates(last_date, h, weekdays=infer_draw_weekdays(history))`. `infer_draw_weekdays` reads the schedule off the recent tail of the data so that a pre-Monday history keeps generating Wed/Sat dates rather than phantom Monday draws.

**Backtest scoring is set-based and order-agnostic.** `lottery/backtest.py:_score_window` compares the *set* of the 5 main-position predictions against the *set* of actual main balls; slot order is irrelevant. This is what makes the exact hypergeometric baseline in `lottery/models/baseline.py` the correct comparison, and it is why order-statistic artifacts in the source data cannot inflate backtest results. Preserve this property in any new scoring code.

**The sorted-data trap.** Official results are often published with the main balls sorted ascending. When that happens each column is an order statistic (min, 2nd-smallest, ...), not a uniform draw, and a per-position chi-square test will report spurious "non-random" structure. `lottery/analysis/randomness.py:is_sorted_ascending` detects this and `pooled_uniformity_test` is the sort-proof alternative (it pools columns and only asks whether every number appears equally often). It takes only the positions to pool and derives the range from them, so pooling the 1-16 superbalota with the 1-43 main balls is not expressible — a mistake that value range-checking cannot catch, since 1-16 is a subset of 1-43. Per-position tests are diagnostics; the pooled test is the verdict. Also note six simultaneous per-position tests produce false positives at the usual rate — the dashboard says so, and any new test surface should too.

**Multiple comparisons are corrected everywhere.** A backtest scores k models against the same draws and `compare_strategies` scores k strategies the same way, so both emit `beats_chance` (naive, α = 0.05) *and* `beats_chance_corrected` (Bonferroni, α/k), and every surface points the reader at the corrected column. With six models the naive bar is cleared by luck ~26% of the time — "one of my six models beat chance" is exactly the sentence a lottery system gets built on. A new evaluation table that reports one uncorrected verdict has reintroduced the bug.

**A null result needs its resolution attached.** (all three domains for the lottery; football now too — `football/power.py` and `football/sensitivity.py`, and the **¿Le gana al mercado?** tab prints what the run could have detected beside what it did, from that run's own measured spread.)  `lottery/analysis/power.py` computes the minimum detectable effect for a given number of draws, and every surface reporting "nothing beat chance" should say what it could have detected: 15 windows cannot see a +75% edge, 1035 draws bottom out at +9%, and the MDE only falls with the square root of N. `lottery/analysis/sensitivity.py` is the other half — it plants a known bias and measures how often each detector fires, so "the tests found nothing" is backed by evidence that they can find something. Its `strength = 0` row is the control; a detector firing well above alpha there means *something* is broken, though not necessarily the thing under test — the first time it fired, the fault was in the harness, not the estimator.

**Suspect the harness before the statistic.** When a control arm misbehaves, check how the experiment was wired before concluding the tested code is wrong. `beats_chance_test` was measured under the null and is calibrated (sd(z) = 0.997 at 1 ticket per draw, 0.927 at 5, against a nominal 1.0), including when several tickets share a draw — so do not add a cluster-robust variance for that; one was written, measured against the exact test, and removed. Measure sd(z) under the null before changing an estimator.

**Chance comparisons are one-sided.** `lottery/models/baseline.py:beats_chance_test` returns `p_value` (two-sided, "differs from chance") and `p_value_greater` (one-sided, "better than chance"). Only the one-sided value may back a "beats chance" claim — a model significantly *worse* than chance also gets a small two-sided p-value.

**One kind of cycling result per frame.** (cycling) A rank of 4 in a stage result and a rank of 4 in a general classification are different quantities — a day's placing versus three weeks of accumulated time — published in the same table layout for the same riders on adjacent pages. `cycling/processor.py:preprocess_results` raises on a frame that mixes kinds and `load_races` raises rather than concatenating files of different kinds; the scraper puts the kind in the filename so they cannot land in one file by accident. This is football's opening/closing trap in a third costume.

**Cycling non-finishers stay in the frame.** (cycling) A fifth of a Grand Tour's start list can fail to finish, and abandons concentrate among the riders in worst form — the ones a model was least sure about. Dropping them turns "predict the finishing order" into the strictly easier "predict the order among those who finished". They are kept with `rank` NaN and a `status`; filtering is an explicit `finishers()` / `finishers_only=True`, and it runs **after** the checks so the "no abandons at all" warning still fires on the file as published.

**`time_seconds` is a total, never a gap.** (cycling) Results pages publish the winner's elapsed time and everyone else's gap to it (`,,` meaning "same time as above"). The scraper resolves gaps against the winner and blanks the whole page's times when the winner's own time is missing — writing gaps into a column that means totals produces a frame that looks normal and has rank 2 four hours ahead of rank 1. `time_order_violations` hunts for that fingerprint afterwards.

**Opening and closing odds are never mixed.** (football) Closing prices are sharp; opening prices are soft, and a model that beats them has usually beaten a bookmaker's first guess. football-data publishes closing odds (`AvgCH`, `B365CH`) only from 2019/20, so a merged history has them for its recent half only. `football/processor.py` resolves **one odds source per frame or none**: rows missing it stay NaN, there is no per-row fallback, a partial price triple is blanked whole, and `load_seasons` raises rather than concatenating files that resolve to different sources. This is the football counterpart of Baloto's two eras and is just as invisible in the frame's shape.

**Odds are not probabilities.** (football) The three implied probabilities of a match sum to 1.02-1.08; that excess is the bookmaker's margin and must be removed before the prices mean anything. A model compared against raw `1/odds` is measured against a baseline deliberately wrong in the bookmaker's favour. `football/market.py` offers three normalisations that disagree on longshots — run `compare_methods`, and if a conclusion flips between them it is about the margin model, not the model.

**Football scoring is proper and ordered.** (football) `football/scoring.py` defaults to the ranked probability score, not Brier, because the outcome H–D–A is **ordered** — a forecast that backed a home win when the away side won is more wrong than one that backed the draw, and RPS charges for that distance. Brier is a symmetric diagnostic; **RPS is the verdict**, the same shape as the lottery's "the pooled test is the verdict". `METRICS = ("brier", "rps", "log_loss")`.

**Closing line value converges where the market test cannot.** (football) `beats_market_test` is the right question and needs thousands of matches to answer, because it is a difference of two noisy proper scores. `football/clv.py` asks the smaller measurable one — did the line move toward the bet — which needs hundreds, because it is a direct measurement that never looks at the result. **Positive CLV is not profit**, and no amount of it is: it says the information was real, not that the edge survives the margin paid to take the bet, which is still `value.py`'s two bars. Colombian extra files are opening-only, so CLV is not computable there and the surface says so rather than quietly not appearing.

**Calibration is a different question from edge, and the surfaces say so.** (football) `football/calibration.py` asks whether a forecast's 30% happens 30% of the time; `football/evaluation.py` asks whether it beats the price. A forecast that simply copies the de-margined closing line is **perfectly calibrated and worth exactly nothing**, which is why every calibration surface carries that sentence and why the dashboard renders the curve *after* the verdict rather than beside it. Two rules follow. A recalibrator is **never fitted on the matches it is then scored on** — `prequential_calibrate` fits each row's correction on the rows before it, the same refusal `ensemble.py` makes about its blend weight — and a recalibrated backtest **drops the leading rows from every model at once**, because mixing rows the correction reached with rows it could not pulls any difference toward zero.

**A football forecast is never shown without the market beside it.** (football) Every dashboard surface that shows model probabilities shows the de-margined market vector next to them and links the measured verdict; a bare model forecast implying the model is good on its own is the football version of presenting a lottery hindcast as a prediction. `football/evaluation.py:beats_market_test` is the verdict: a **paired one-sided** test of `market_score − model_score` per match against `null_mean = 0`, through `core/significance.py`, emitting `beats_market` and `beats_market_corrected` together (bump `n_comparisons` when scoring several models against the same matches).

**Extra files are opening-odds-only.** (football) `football/extra_processor.py` (the `new/COL.csv` contract — Colombia, Argentina, Brazil, Mexico, USA) pins `attrs["odds_are_closing"] = False` and always resolves `odds_source` to an `extra_*_opening` name; it also enforces one `League` value per load (`MatchFormatError` otherwise, `league=` to pick one). Because the baseline is the soft opening line, **no corrected edge claim is possible on Colombian data** — a model that beats those prices has beaten a bookmaker's first guess, not the market. Reached with `python -m football.downloader --leagues COL --extra` and `football.backtest --extra --league`.

**Several models are scored on the same held-out set, or not compared at all.** (football, cycling) `compare_models` skips a window *any* requested model cannot predict, for **all** of them, and `compare_forecasters` drops a race where either side is NaN from both. Two models scored on different subsets are not comparable, and nothing in a results table's shape would reveal it. `n_comparisons` is then the number of models/challengers, so the corrected threshold tightens as you add one — which is the correct direction.

**A blend at weight 0 is the market, exactly.** (football) `football/ensemble.py` pools a model with the price, and the endpoint is load-bearing: at weight 0 the blend scores identically to the market and the paired test returns an effect of exactly 0. That is what makes any gain as the weight rises readable as "the model carries information the price does not" — a more answerable question than "does it beat the market", which almost nothing does. A test pins both endpoints; if they drift the reading is gone. Nothing in the module is fitted, because fitting the weight on the matches you then score is the leak this repo exists around.

**There are two bars in football and they are different.** (football) A **model** is judged against the de-margined price (`market.py`, `evaluation.py`); a **bet** is judged against the raw `1/odds`, because you pay the margin. Between them is a band where the model disagrees with the market and the disagreement cannot pay for the spread — which is where most betting systems live. `football/value.py:classify` makes it a named state (`no_value` / `disagreement_only` / `value`) rather than a footnote, and `margin_cost` prints its width. Kelly defaults to a **quarter** stake and the dashboard shows no stake until the measured verdict is beside it: on an edge that is not real, full Kelly sizes up precisely when the model is most confidently wrong.

**Cycling's non-finishers stay in the scoring denominator.** (cycling) `cycling/scoring.py` places riders one at a time against everyone not yet placed, and "everyone" includes the abandons — so a forecast that backed a rider who climbed off is charged for it. Dropping them silently renormalises the field to the riders who finished, turning "predict the finishing order" into the strictly easier "predict the order among those who finished". This is the same rule the data contract already enforces, restated as arithmetic so it cannot be forgotten rather than as a check that must be remembered.

**A uniform draw over a cycling start list is not a baseline.** (cycling) At ~180 riders it gives everyone 0.55%, which any forecast beats by knowing one name. `cycling/baseline.py:uniform_worths` implements it under that name and says so, and the dashboard keeps it in the comparison table where it loses to the ranking — an unnamed mistake is one that gets made quietly.

**Order-agnostic summaries are a second, independent verdict.** `lottery/analysis/structure.py` compares the sum, odd count and calendar split of each draw against their exact combinatorial distributions. The pooled test asks about marginals and a machine can pass it while broken — five consecutive numbers use every number equally often and still have sums far narrower than combinatorics allows. These see that. They are also immune to the sorted-data trap for a stronger reason than the pooled test is: sorting cannot change a property of the *set*, so the outputs are bit-identical under a column shuffle, and a test asserts it.

**A forward record exists in every domain, and is scored against that domain's bar.** `core/registry.py` holds the three refusals; `lottery/analysis/registry.py`, `football/registry.py` and `cycling/registry.py` supply what a prediction is and what it is measured against — chance, the de-margined closing price, the pre-race ranking. The lottery had this first, which is where it means least, since everyone already knows Baloto cannot be beaten; the other two are where a forward record would be evidence. Each domain's endpoint is pinned: a football forecast that *is* the market accumulates exactly zero, a cycling forecast that *is* the ranking scores exactly zero against it.

**A result carries what produced it.** Every walk-forward and holdout entry point attaches a
`core/manifest.py` manifest — `lottery/backtest.py`'s `run_all` and `run_holdout` (on each result frame's `attrs`
and carried through `summarize` to the table people actually read), `football/backtest.py`'s `compare_models`
(`attrs`) and `run_all` / `run_holdout` (a `manifest` key, which the CLI prints as one compact provenance line),
and `cycling/evaluation.py`'s `walk_forward` / `compare_forecasters` (`attrs`). Note `attrs` does not survive most
pandas operations, so it is copied explicitly rather than inherited. The dirty flag is the load-bearing field:
a result produced from an edited working tree is reproducible from no commit at all, which is the state most
results are looked at in. A new evaluation entry point that attaches no manifest looks identical in every results
table, so `tests/test_core_manifest.py` pins the wiring for all three domains.

**Effect sizes travel with p-values.** `core/significance.py:z_test_against_null` returns `effect`, `ci_low`, `ci_high`, `relative_effect` and `n_observations` alongside both p-values, and `beats_chance_test` passes them straight through. A p-value alone cannot distinguish "no edge" from "no edge detectable here" — report the interval.

## Module layout

- `core/significance.py` — `z_test_against_null` (both p-values, effect size, confidence interval), `bonferroni_threshold`, and `verdicts`, which returns the naive and corrected verdicts together so no surface can report one without the other. Domain-free: the caller supplies the null's mean and variance.
- `core/windows.py` — `window_bounds` (walk-forward) and `cutoff_bounds` (date holdout). Pure index arithmetic over an ordered sequence.
- `core/manifest.py` — provenance. `run_manifest(inputs)` records the commit, **whether the tree was dirty**, the UTC time, the Python version and the versions of the libraries whose arithmetic can move a number; `data_fingerprint(frame)` / `combined_fingerprint(frames)` hash values, columns *and* dtypes, so a single corrected cell or a moved column changes the digest where a row count would not. Domain-free: the caller names its own `inputs`.
- `core/registry.py` — pre-registration, domain-free. A `RegistrySchema` names each domain's event, prediction and result columns and `core/` assembles the file from it; the three refusals live here and **none may soften into a warning**: an event already past is rejected, a second prediction for the same (event, label) is rejected, and `score_pending` scores every resolvable row or none — a `resolve` returning None means "not yet" and is the only reason a row may be skipped. `status` deliberately says nothing about how good the predictions are, because what counts as resolution is a domain question.
- `core/storage.py` — a store that refuses to lose the shape of what was put in it, domain-free. **SQLite, not Parquet**, and the deciding reason is appending: appending to Parquet means writing *another file*, which reintroduces the multi-file drift `load_seasons` and `load_races` refuse to concatenate through; SQLite is stdlib, appends in place and keeps its own metadata table. `write_frame` / `append_frame` / `read_frame` / `table_info` record the schema version, columns, **dtypes**, row count and a `core/manifest.py` fingerprint. It refuses a version mismatch on read, a renamed/reordered column or a **dtype drift** on append (pandas concatenates float onto int without complaint, leaving a column that means two things), an **empty write** (a scraper writing nothing when the markup changed is the failure mode the parsers are shaped against), and a duplicate key unless the caller says which copy wins — there is no "overwrite", because silently replacing a stored row with a re-scraped one turns a corrected result back into an uncorrected one. **Dtypes are restored, not re-inferred:** SQLite has no datetime type and an ISO date string compares correctly against another ISO date string, so the bug survives every casual test and fails on the first arithmetic.
- `core/ledger.py` — what was actually **staked**, kept apart from what was forecast. `core/registry.py` holds a claim scored against the domain's bar; this holds money, in its own file, because a row that was both would be read as whichever suits. **The headline is the verdict, never the running total**: `summary`'s column order puts `beats_breakeven_corrected`, the p-value and `min_detectable_return` before `profit` and `roi`, so a surface rendering it in order cannot lead with a P&L — the one number that looks like evidence, moves daily, and at the sample sizes a person reaches cannot tell an edge from a good run. The null is **break-even, generously**: a no-edge bettor paying the margin has a negative expectation, so zero is a bar they sit below rather than merely fail to clear. Variance is **measured** from the settled rows (per-bet returns have no closed form — it depends on the prices taken), the same call `football/power.py` makes. The registry's three refusals restated for money: a stake on an event already past, an edit to a settled row, and settling a subset.
- `lottery/models/common.py` — ball ranges, draw calendar, position helpers, long-format conversion. Everything else imports its constants from here.
- `lottery/models/baseline.py` — exact hypergeometric chance baseline and `beats_chance_test`, the domain half of the contract with `core/significance.py`: it turns `m_guessed` into a per-draw mean and variance and renames `null_mean` to `chance_mean`. `m_guessed` accepts a per-window list because collisions between positions change the distinct-guess count.
- `lottery/models/statsforecast_model.py` — AutoARIMA/AutoETS/AutoTheta via Nixtla. `fit_predict_all` fits **every position and all three models in one call**; don't loop per position for these.
- `lottery/models/xgboost_model.py` — chronological splits only. The original code used a shuffled `train_test_split`, leaking future draws into training; keep splits time-ordered.
- `lottery/models/prophet_model.py` — Prophet per position. Named `prophet_model`, not `Prophet`, so importing it cannot shadow the `prophet` package it depends on.
- `lottery/models/timesfm_model.py` — Google's TimesFM, the one model that **fits nothing**: a pretrained transformer forecasting zero-shot from a context window, on the sequential draw axis (values, not dates). `is_available()` / `best_device()` / `load_forecaster` / `forecast_positions` / `forecast_horizon_positions` / `CheckpointUnavailableError`. All positions go in **one batched `forecast()` call**, the same rule as `fit_predict_all`. The point of including it is the premise: a foundation model failing the same chance test as a 3-line frequency baseline is a far stronger statement than the baseline failing alone, so it is scored through the identical `_score_window` and Bonferroni correction with no special treatment.
  - **This project runs locally, and the defaults are the strong ones because of it** ([`docs/local-setup.md`](docs/local-setup.md)): the **3.0** checkpoint, `MAX_CONTEXT = 2048` (a full history is ~1035 draws, so nothing truncates), and the GPU via `best_device()` (cuda → Apple `mps` → cpu). An earlier version pinned 2.5 and a 512 context to fit a hosted free tier; do not reintroduce either without a reason that is not hosting.
  - **Licence is the one restriction local use does not remove**: weights up to 2.5 are Apache-2.0, **3.0's are non-commercial/non-production**. Local research is inside those terms; a public URL or anything commercial is not, and `CHECKPOINT = CHECKPOINT_APACHE` is the switch. Nothing here redistributes weights.
  - **The two checkpoint families have different APIs** — 2.5 compiles a `ForecastConfig` and exposes `.forecast(horizon, inputs)`, 3.0 takes a `device` and exposes `.predict_batch(...)`. `_Timesfm3Adapter` normalises 3.0 to the 2.5 shape so the difference never reaches `forecast_matrix`, the backtest, the dashboard or the tests.
  - torch plus the checkpoint are still the heaviest thing in the project, so `is_available()` uses `find_spec` and **must not import torch** (the dashboard re-executes on every interaction), and a missing install makes the surface *say so* rather than quietly offer one model fewer. `forecast_positions(..., forecaster=)` is injectable, which is how the suite pins its invariants without a checkpoint (CI installs neither timesfm nor torch).

- `lottery/analysis/randomness.py` — frequency, gaps, hot/cold, chi-square (per-position and pooled), runs test, ACF/Ljung-Box.
- `lottery/analysis/structure.py` — order-agnostic summaries against their **exact** combinatorial references: `sum_distribution`, `parity_distribution`, `range_split_distribution` (calendar split at 31), `goodness_of_fit`, `structure_report`, `sum_percentile`. Not a restatement of the pooled test — that one asks about marginals and a machine can pass it while broken (five consecutive numbers use every number equally often and still have impossible sums). Immune to the sorted-data trap for a stronger reason than the pooled test: sorting cannot change a property of the *set*. `goodness_of_fit` pools thin tails before the chi-square and returns NaN rather than a verdict below two surviving cells.
- `lottery/analysis/tickets.py` — generate tickets (random/hot/cold/model/portfolio), check them against draws, and `evaluate_strategy`/`stability_check`, which measure whether a generation strategy beats chance. `stability_check` exists because a single run flags a signal-free strategy ~1 time in 20; `random` is the control whose flag rate is the measured false-positive floor.
- `lottery/analysis/power.py` — minimum detectable effect, required draws, power curves. Mirrors the z-test in `baseline.py` exactly, since the point is to characterise that test. The superbalota helper is separate because it is Bernoulli, not hypergeometric — using the wrong variance understates the required data ~3x.
- `lottery/analysis/sensitivity.py` — plants a known bias and measures detection rates for `pooled`, `hot` and `random`. `random` must stay near alpha even on biased data (a uniform ticket's expected matches do not depend on the weighting) — that is the control, not a failure. **Its own load-bearing detail:** the draw generator and the ticket generator must be driven by *independent* streams, via `independent_seeds`. Passing one seed to both makes the numbers drawn and the numbers played come out of the same `default_rng`, which is a real ticket/draw dependence — exactly what a lottery test hunts for. That mistake reported a 17.5% false-positive rate on bias-free data and sent a full round of investigation after a phantom defect in `evaluate_strategy` (see `docs/evaluation.md`). Any new detector needing randomness takes its seed from `independent_seeds`.
- `lottery/analysis/popularity.py` — jackpot splitting. The only module here that improves anything, and it improves `E[payout | win]`, never `P(win)`. `popularity_score` is **ordinal**, not absolute: its weights cannot be calibrated without data on tickets people bought, which no operator publishes, so `split_adjusted_value` returns a band rather than a figure. Registers `unpopular` in `STRATEGIES`, which correctly fails the hit-rate tests — the accuracy machinery is structurally unable to measure what it targets, and that is documented rather than exempted.
- `lottery/analysis/registry.py` — the lottery's adapter onto `core/registry.py`. Supplies what a prediction is (5 main numbers + superbalota), how to score one against a draw, and the minimum detectable effect `core`'s `status` deliberately omits. Public API and file unchanged by the lift, and its tests passed **unchanged** — that is the refactor's proof. Writes `predictions.csv` at the repo root, deliberately **not** gitignored: committing it dates each prediction in version control, which beats any timestamp the file writes about itself.
- `lottery/analysis/prizes.py` — exact prize-category probabilities, expected value, RTP, breakeven jackpot. Pure combinatorics, needs no historical data. Prize amounts are caller-supplied, never hardcoded, because tiers are operator-set and the top prize accumulates.
- `lottery/backtest.py` — walk-forward evaluation. `run_all` holds out the last N draws; `run_holdout(..., cutoff, mode=)` holds out everything after a date, either refitting per draw (`expanding`) or from one fit at the cutoff (`frozen`). Both score through the same `_score_window`, so their summaries are comparable.
- `dashboard/` — the Streamlit UI, the primary surface: **one app, three domains, chosen from a sidebar selector**. `app.py` is only the shell (page config, selector, dispatch) and imports each page **lazily**, since Baloto's pulls in statsforecast and xgboost. `baloto_page.py`, `football_page.py` and `cycling_page.py` each export `render()`. The `_page` suffix is load-bearing: Streamlit puts the script's directory on `sys.path`, so a `dashboard/football.py` would shadow the `football/` package it imports — the same trap `prophet_model.py` is named around.
  - **`DOMAINS` in `app.py` carries a one-line state per domain**, shown under the selector. All three now have a baseline, a scoring rule and a walk-forward evaluation, but they are **not the same bar** and the caption names which one: chance for Baloto, the closing price for football, the pre-race ranking for cycling. The domains differ in what can be found in them at all, not in how far the code has got.
  - **`dashboard/mobile.py` owns the phone layout**, installed once by the shell before any page renders, for the same reason `ui.py` owns the copy: three page modules each patching their own CSS cannot be reviewed as a whole. Every CSS rule sits **inside a `max-width: 640px` media query**, so a wrong rule is wrong only on phones; columns stack except those holding a metric, which go two-up. `mobile.responsive(fig)` is applied by `ui.chart` to every figure — it moves the Plotly legend off the right-hand side (a vertical legend costs a third of the width at 375px) and turns off drag and scroll-zoom, so a finger on a chart scrolls the page. **Do not set the sidebar's width**: Streamlit collapses it by translating a fixed number of pixels, not by its own width, so widening it parks a strip of sidebar over the ☰ button — and on a phone every control is behind that button. Verify with Playwright at a phone viewport, asserting `scrollWidth == innerWidth` and that `elementFromPoint` at the ☰ button returns the button. See [`docs/local-setup.md`](docs/local-setup.md).
  - **`dashboard/betlog_page.py` owns the stake log**, shared by the domains that have a price, for the same reason `ui.py` owns the copy and `mobile.py` owns the phone layout: three pages each building their own log could not be reviewed as a set, and "the headline is the corrected verdict, never the running total" is exactly the kind of rule that erodes one page at a time. It renders counts, then the verdict, then what this many bets could have detected, and only then the money under a caption saying why it is last. Recording goes through `core/ledger.py`'s refusals — the dashboard is another caller of them, not a way round them. Ledger and registry files are deliberately **not** gitignored, for `core/registry.py`'s reason: committing them dates each row in version control.
  - All explanatory copy lives in `dashboard/ui.py`, in **four dicts keyed identically** (keys prefixed `fb_` / `cy_` for the newer domains) so one key carries every layer: `HELP` (the hover ⓘ), `PLAIN` (an always-visible box — *qué estás viendo · qué puedes concluir · **lo que NO significa***), `READ` (a one-line "cómo leerlo" under a chart title) and `GLOSSARY` (the jargon, once, with an example each). `section(title, key)` and `chart(fig, title, key)` pull `PLAIN` and `READ` in automatically off the key they already take, so no call site changes and copy cannot drift into a page module. `PLAIN`'s third field is **required by the shape and enforced by a test**: it is the sentence that stops a reader leaving with the conclusion a surface merely looks like it supports. `plain_verdict(passed, headline, detail, good_is_pass=)` states a finding in words with the number underneath; `good_is_pass=False` is for the cases where failing is the welcome outcome. `glossary()` puts the expander in a page's sidebar. Tab labels carry a 1-based number, because ten unordered tabs read as ten equally good places to start. Splitting the pages into modules was the moment that rule was easiest to lose — three files with their own inline strings cannot be reviewed as a whole, which is the only way the "no chart appears without saying what it does *not* mean" rule is checkable. `chart` moves the title out of the Plotly figure because Plotly's own title has nowhere to hang a help icon — clear it with `title={"text": ""}`, since `title=None` makes Plotly render the literal string `undefined`. A bare `st.plotly_chart` outside that helper means a chart was added without an explanation.
  - The football and cycling pages surface their domain's refusal rather than working around it: selecting season files with different odds sources, or a stage result together with a general classification, renders the error (Spanish explanation, original message as detail) instead of merging.
  - `football_page.py` has six tabs (Datos · Mercado · Pronóstico · ¿Le gana al mercado? · Valor · Registro) and a Europa/Colombia source toggle. **Pronóstico** is the two-team view (H2H + Dixon-Coles 1X2 + Elo + scoreline heatmap + O/U + BTTS); model probabilities are shown only beside the de-margined market, never alone. **¿Le gana al mercado?** gates the multi-model backtest (both verdicts, corrected emphasised). **Valor** shows no stake until that verdict is on screen beside it, and draws the margin as a stacked band so a model sitting inside it reads as what it is — a disagreement that cannot pay for the spread. **Registro** is the forward record: the model beside the de-margined market at the prices the reader can actually get, a write into `football/registry.py` (which refuses a fixture already kicked off and a duplicate label), the forward verdict against the closing line, and — separately, below — the stake log. **Valor is rendered after the backtest block, not beside Pronóstico**: Streamlit runs every tab body per rerun in source order, so an earlier Valor reads the verdict one rerun stale. Colombia mode always shows the opening-odds warning on model surfaces.
  - `cycling_page.py` has seven tabs (Datos · Abandonos · Tiempos · Pronóstico · Terreno y forma · ¿Le gana al ranking? · Registro). **Registro** writes a start list and its worths as **one** forecast into `cycling/registry.py` and carries the stake log; its verdict is against the ranking, not the market, and says so, because nothing here fetches cycling prices. **Pronóstico** builds the ranking baseline and the fitted model for one race from results strictly before its date and shows them together, with the uniform draw drawn as a dotted line; its terrain selector is filled in by **the reader, from the roadbook**, and the caption says how many past races of that terrain were behind the fit or that it fell back to the unconditional one — inferring the target race's terrain from its own result would be leakage that looks identical to the honest label. **Terreno y forma** is descriptive only: the inferred terrain of each past race beside `features.py`'s per-rider columns, carrying the warning that where sprints are near-random every strong rider reads as a climber. The walk-forward stays unconditional, because the contract has no roadbook column. **¿Le gana al ranking?** gates the walk-forward and keeps the uniform draw in the table on purpose — it comes out worse than the ranking, which is the demonstration that it is not a baseline.
- `lottery/utils/check_docs.py` — the documentation link checker described above.
- `football/common.py` — the three outcomes and the `(home, draw, away)` ordering every probability vector, score and column triple in the package follows. Transposing two of them is a bug no range check can catch, since all three are valid probabilities.
- `football/processor.py` — the football-data.co.uk contract and the opening/closing guard described above.
- `football/market.py` — decimal odds to calibrated probabilities. `overround`, `implied_probabilities` (multiplicative / additive / power), `market_probabilities` for a whole frame, and `compare_methods`. This is football's `baseline.py`.
- `football/downloader.py` — football-data.co.uk season files into `exported_data/football/`. Downloads rather than scrapes (the site publishes CSV), writes each file **exactly as downloaded** because `processor.py` owns the contract, but routes it through `preprocess_matches` first so a format change is caught at download time. Sniffs for an HTML error page served with a 200 — `pd.read_csv` would turn one into a plausible one-column frame — and refuses to replace a longer file with a shorter one without `--force`. `--extra` + `EXTRA_LEAGUES` (COL, ARG, BRA, MEX, USA) fetches the `new/{code}.csv` files via `download_extra`, routed through `preprocess_extra`; `--seasons` is ignored there and without `--extra` those codes are refused by name.
- `football/extra_processor.py` — the `new/COL.csv` contract (`Home`/`Away`/`HG`/`AG`, leagues and seasons stacked, opening odds only). `preprocess_extra(df, league=None, validate=True)`, `load_extra`, `available_leagues`; maps onto the same tidy frame as `processor.py` so model/market/scoring/dashboard consume it unchanged. `EXTRA_ODDS_SOURCES` are all `extra_*_opening`; `attrs["odds_are_closing"]` is always `False`; more than one `League` value without `league=` raises `MatchFormatError`.
- `football/calibration.py` — does a 30% mean 30%? `reliability_curve` / `expected_calibration_error` (a bin below `MIN_BIN_COUNT` reports its count and **no** frequency, the `goodness_of_fit` rule again), `calibration_in_the_large` (mean forecast vs base rate per outcome — **two-sided**, deliberately, since under-forecasting is mis-calibration too, and emitting `miscalibrated` / `miscalibrated_corrected` because it is three tests over one set of matches), `TemperatureScaler` (one parameter, fitted in logs so it cannot cross zero), `IsotonicCalibrator`, and `prequential_calibrate`, **the gate**: each row's correction is fitted on the rows strictly before it and the leading `min_fit` rows pass through untouched. Reached from `backtest.compare_models(..., calibrate=)`, which then trims every model, the market and the outcomes by the same amount so the comparison stays on one set of matches.
- `football/power.py` — what edge this many matches could have revealed. Mirrors `beats_market_test` the way `lottery/analysis/power.py` mirrors `beats_chance_test`, with one real difference: the paired score difference has **no closed-form variance**, so `observed_score_sd` measures it from a run that happened and every function takes it as an argument. `REFERENCE_SCORE_SD = 0.08` is a measured fallback, not a guess — the 0.05 that preceded it was a guess and was wrong by 2-5x, and counts scale with its square. A season of one league bottoms out near **0.010** of RPS.
- `football/sensitivity.py` — plants a known edge by blending the generative truth into the forecast and measures how often `beats_market_corrected` fires. **`strength = 0` is a forecast that *is* the market** and is the false-positive floor. Two measured findings live in its docstring: at `market_noise = 0` the dial is inert because a perfect price leaves nothing to know, and **detection falls as the planted edge grows** because the spread outruns the effect — `ensemble.py`'s case for pooling, from another direction. Seeds come from `independent_seeds`.
- `football/clv.py` — closing line value: did the price move toward the bet after it was taken? `join_prices` (explicit, raises on no overlap, reports `n_dropped`), `paired_prices` (both ends out of **one** football-data file from 2019/20 on, by running `preprocess_matches` twice — once as published, once with the closing columns dropped — so the one-source-per-frame guard still does the work), `clv`, `clv_table`, `beats_closing_test` (one-sided, `beats_closing` / `beats_closing_corrected`), `clv_report`, `summarise_by_outcome` (a diagnostic; reading the best of three slices is the mistake corrected everywhere else here). **De-margined on both ends**: a book that widens its margin moves every raw price against every bettor, and a raw-price CLV reads that as everyone losing value. The endpoint pins the meaning — **CLV against the price you bet is exactly zero**, the same load-bearing zero as a weight-0 blend.
- `football/registry.py` — a forward **market** test, not a forward accuracy number: a row stores the forecast's RPS, the de-margined closing price's RPS on the same match, and their difference, and `summary` runs that difference through the same one-sided paired test as `evaluation.py`. The bar is supplied at scoring time, so it too was unfalsifiable when the forecast was written; a fixture with no usable price stays **pending** rather than being scored against nothing. Endpoint: a forecast that *is* the market accumulates exactly zero.
- `football/scoring.py` — proper scoring rules for the three-way outcome: `brier_score`, `ranked_probability_score`, `log_loss`, `per_match_scores(probs, outcomes, metric)`, `skill_score`. `METRICS = ("brier", "rps", "log_loss")`; **RPS is the default** because H–D–A is ordered.
- `football/h2h.py` — `team_form(matches, team, last_n=5, as_of=None)` and `head_to_head(matches, home_team, away_team, as_of=None)`. Descriptive only — no probabilities, no claim of predictive value.
- `football/dixon_coles.py` — `DixonColes` (classmethod `.fit(matches, half_life=None, max_iter=200)`): params `mu` / `home_advantage` / `attack` / `defence` / `rho` (bounded ±0.4). `.scoreline_matrix`, `.predict_outcome` (H–D–A order), `.most_likely_scores`, `.over_under`, `.both_teams_to_score`, `.predict_matches`; `UnknownTeamError`; module fn `independent_poisson_matrix`. `_tau` is the low-score correction; `half_life` weights the likelihood `0.5 ** (age_days / half_life)`.
- `football/evaluation.py` — `beats_market_test(model_probs, market_probs, outcomes, metric="rps", alpha=0.05, n_comparisons=1)`: a paired one-sided proper-score test of `market_score − model_score` per match against `null_mean = 0`, through `core/significance.py`. Returns `beats_market` / `beats_market_corrected` (the `core` `beats_chance*` keys renamed for the domain) plus the effect and its interval. This is football's `beats_chance_test`.
- `football/elo.py` — `Elo.fit(matches, k=20, home_advantage=60)`: ratings advanced **one matchday at a time** (every fixture on a date predicted from the ratings before that date, updates applied together afterwards — match-by-match updating would make the fit depend on row order within a matchday and let one 3pm result inform another). The rating gap maps to H-D-A through an **ordered logit** whose two cut points and scale are fitted by MLE; the gap is optimised in logs so the cuts cannot cross. `.predict_outcome`, `.predict_matches`, `.rating`, `.rating_gap`, `.ranking`. No scoreline — one strength number cannot produce one.
- `football/ensemble.py` — `linear_blend`, `logarithmic_pool`, `blend(..., pool=)`, `POOLS`. A blend at weight 0 **is** the market and scores identically, so any gain as the weight rises is information the model has and the price does not — a more answerable question than "does it beat the market". Linear hedges; logarithmic leans on agreement and is harsh on what one source nearly ruled out. Nothing here is fitted: fitting the weight on the matches you then score is the leak this package exists to avoid.
- `football/bankroll.py` — an edge is a number; a bankroll is a path. `simulate_bankroll` (bootstrapped paths), `drawdown_distribution` (measured from the running peak, since that is where a person actually stops), `risk_of_ruin` (**ever**, not at the end), `roi_interval`, `summarise`, `stake_fraction_sweep`. **Every simulation carries a null path** — the same selections and stakes with outcomes redrawn from the de-margined market — because a lone upward curve reads as a promise. Note the obvious null does not work: re-staking from the market's own numbers produces a bettor who never bets, since a de-margined probability never clears the raw price (the two bars, working). Measured: at full Kelly a model handed the **exact generative truth** still stakes 88% of bankroll on one match and is ruined in 99% of paths, against 9% at a quarter.
- `football/uncertainty.py` — bootstrap bands on predicted probabilities, and the downgrade they force. `bootstrap_predictions` (resample, refit, quantile; non-finite refits are filtered, not propagated — one NaN otherwise erases every band), `band_width`, `downgrade_uncertain_value`, `with_bands`. **Bootstrap rather than a Hessian because `rho` is bounded**, and `attrs["n_at_bound"]` measures it: at 20 matches 76 of 80 refits end against a bound, where a curvature estimate describes a wall. A `value` call whose band crosses `1/odds` is demoted to `disagreement_only`; **nothing is ever upgraded**.
- `cycling/uncertainty.py` — the same for rider worths, resampling **races** rather than riders (a finishing order is one observation). Two measured surprises: the **absolute** width narrows with races while `relative_band_width` moves in either direction and is a within-fit ranking only; and a percentile band **need not contain the point** — `contains_point` flags those rather than correcting them, since they are the fit naming which numbers it would not reproduce.
- `football/value.py` — `break_even_probability`, `expected_value`, `kelly_fraction`, `classify`, `value_table`, `margin_cost`. Built around **the two bars being different**: a model is judged against the de-margined price, a bet against the raw `1/odds`, and the margin sits between them. `classify` names that gap (`no_value` / `disagreement_only` / `value`) because it is where most betting systems live. Kelly defaults to a **quarter** stake — on an edge that is not real, full Kelly sizes up exactly when the model is most confidently wrong. One outcome at a time; the joint case over-stakes with this formula.
- `football/backtest.py` — walk-forward evaluation, mirroring `lottery/backtest.py`. `run_all(matches, n_windows=30, min_train=100, half_life=None, method="multiplicative", metric="rps", model="dixon_coles")` holds out the last N matches; `run_holdout(matches, cutoff, mode="expanding"|"frozen", ...)` holds out everything after a date; `compare_models(..., models=MODEL_NAMES, blend_weight=0.5, pool="linear")` scores several over the **same** held-out matches and returns one row each. A window any requested model cannot predict is skipped for **all** of them — two models scored on different matches are not comparable and nothing in the table's shape would say so — and `n_comparisons` is the model count. CLI: `python -m football.backtest --seasons ... [--n-windows N] [--cutoff DATE --mode frozen] [--half-life 180] [--method power] [--models a,b,c] [--extra --league "..."]`.
- `cycling/common.py` — result kinds, finish statuses, cycling time parsing. `normalise_status` raises on an unknown rank marker rather than defaulting to "not ranked", which is how a changed page gets noticed instead of quietly losing riders. `OTL` is deliberately not a finisher.
- `cycling/baseline.py` — the bar a model must clear, as a distribution. `worths_from_points` / `worths_from_rating` / `form_worths(results, riders, as_of=)` produce Plackett-Luce worths; `win_probabilities`, `predicted_order`, `sample_orders` (Gumbel-max), `top_n_probabilities`, `baseline_frame`. `uniform_worths` is implemented **and documented as not a baseline** — at ~180 riders it is 0.55% each and any forecast beats it by knowing one name; it exists so the mistake has a name. `form_worths` uses only results strictly before `as_of`.
- `cycling/market.py` — the hard bar, where a price exists. `overround`, `implied_probabilities` (a whole field at once, not a triple — a partial field normalised against the wrong total is the characteristic mistake and is refused), `worths_from_market`, `market_frame`, `compare_methods`, `field_worths`. An outright book runs to a margin of 40%+ (`overround` reports the **excess**, football's convention — two same-named functions meaning different things is a trap nobody catches by reading either one), so the three normalisations disagree far more than in football: **`additive` is kept as a named mistake** — it drives 106 of 180 runners negative and the clip-then-renormalise makes the result *look* like a distribution, which is why `n_zeroed` is reported. `power` is the default because multiplicative scaling leaves the favourite-longshot bias fully intact, and on this market that bias is 170 of the 180 riders. `field_worths` fills the riders the book never quoted with **the longest price it did quote** rather than a zero (a zero takes the log score to minus infinity the first time one of them wins) and returns `n_unpriced` beside the worths; the fill is deliberately unflattering to the market, so a model beating it has not yet beaten the book.
- `cycling/prices.py` — the price contract, and its guards are about identity rather than values: every number in a mixed frame is a valid price. One **book** per frame (two books quote different fields at different margins, so a 176-rider race ends up with 240 priced runners) and one **market** per frame (a GC price beside a stage price normalise against each other and describe a race nobody ran); `load_books` refuses to concatenate files resolving to different books, `market_slice` cuts one market back out. `market_forecaster(prices)` is the `walk_forward` shape, so the market slots into `compare_forecasters` as the baseline; two races priced on the same day are not scored rather than guessed between. Endpoint: a forecast that *is* the market scores exactly zero against it. **Nothing in the repo fetches prices** — this is the shape one must have, not a pipeline.
- `cycling/registry.py` — riders and worths stored together as **one** prediction (splitting them across 180 rows would let half be scored and half not), scored by the Plackett-Luce log score against `form_worths` built strictly from earlier results. A race whose result carries a different field from the one registered is **refused, not rescored** — shrinking the field turns a recorded claim into the strictly easier one. Endpoint: a forecast that *is* the ranking scores exactly zero against it.
- `cycling/scoring.py` — `METRICS = ("plackett_luce", "winner_log", "winner_brier")`; **the Plackett-Luce log score is the verdict**, the only rule proper over a whole ordering. Lower is better. `spearman` / `kendall_tau` / `top_n_accuracy` are diagnostics — a rank correlation rewards getting the middle of the bunch right, which is the worthless part.
- `cycling/features.py` — what one strength number leaves out: terrain, specialisation, team strength, fatigue. **Terrain is known before a race; a result's terrain is not** — `infer_terrain` reads the share of finishers on the winner's exact time (0.80 on a bunch sprint against 0.01 in the mountains, measured, so the 0.5 cut is the middle of a gap rather than a tuned number), which is legitimate for history and **leakage for the race being predicted**, and the leak is invisible because a label read off tomorrow's result looks identical to one read off a roadbook. So `terrain_of` raises for a race at or after `as_of`, and the target race's terrain arrives through `roadbook(dates, terrains)` from outside. `team_strength` **excludes the rider it describes** (otherwise it is their own form wearing a team jersey, counted twice) and fatigue counts **race days, not calendar days**. Every feature goes through one `_history` call whose `<` is `form_worths`' refusal.
- `cycling/plackett_luce.py` — `PlackettLuce.fit(results, prior_strength=5.0, half_life=None)`, rider strengths by Hunter's MM iteration (monotone by construction). `prior_worths=` moves the shrinkage target off the field average, which is what makes `TerrainPlackettLuce` a refinement rather than a noisier copy: the whole calendar is fitted first, then each terrain's races on top of it with the unconditional worths as the prior mean, and a rider with no races of that terrain **keeps their overall worth** rather than being reset to the field (the reset was a real defect and an invisible one — it produces a perfectly ordinary number). A terrain under `MIN_TERRAIN_RACES` falls back to the unconditional fit and `available` says so. Measured on the synthetic races with `sample_data`'s new `specialisation` dial: the effect grows with the planted specialisation (+0.043 → +0.080 at 15 races) and is positive even with **no** specialists, because a flat stage in that generator is nearly pure noise and conditioning excludes it — terrain buys weighting the informative days, not only finding specialists. Nothing clears the corrected bar at 15 races; at 54 it clears it easily. `docs/cycling.md` §11 has the table. The Gamma prior is **not** a tuning knob: without it a rider nobody finished behind has an unbounded worth and one who never finished ahead has a worth of zero, which takes a logarithm to minus infinity downstream. An unseen rider gets the field average, not a refusal — unlike football, a start list with three neo-pros is an ordinary day.
- `cycling/evaluation.py` — `beats_baseline_test` (paired, one-sided, through `core/significance.py`, emitting `beats_baseline` / `beats_baseline_corrected`), `walk_forward` and `compare_forecasters`. No separate backtest module: the walk is five lines and keeping it beside the test is what shows the two share an `as_of`.
- `cycling/processor.py` — the result contract and the three invariants above.
- `cycling/scraper.py` — procyclingstats.com into the contract. `parse_results_page(html, ...)` does no I/O, so it is testable against saved HTML. It finds the results table **by its header row**, not by CSS classes (a class selector that misses returns zero rows, the exact failure this repo's scrapers are shaped against), ranking candidate tables by recognised columns then length — `HEADER_ALIASES` is the one place to teach it a renamed column. Missing pages are skipped and named; anything structural raises from any page.
- `cycling/sample_data.py` — seeded synthetic stage races carrying `ability_true` as the answer key (tests only). Models bunch finishes, abandons that never reappear, and terrain, because leaving any of the three out makes every downstream test easier than reality. `specialisation=` (off by default, and drawing no extra randomness at 0, so seeded fixtures are unchanged) gives a rider a separate `climb_true` and `sprint_true`, which is what lets the terrain question be asked in a world where the answer is known.
- `football/sample_data.py` — seeded synthetic seasons that carry the **generative truth** as `p_true_*`, computed exactly rather than simulated. On real data nobody knows the answer; here they do, which is what lets a test check that a forecast which *is* the truth beats the market. `market_noise` controls how sharp the simulated book is; at 0 it prices the truth exactly. `p_true_*` are an answer key — nothing outside tests may read them.
- `scripts/` — CLI entry points, run as `python -m scripts.<name>`. `summary_charts.py` is the original static matplotlib/seaborn set, superseded by the dashboard for exploratory use.
- `tests/` — the invariant suite. Mirrors the layout above; `pytest -m "not slow"` skips the runs that fit real models.
